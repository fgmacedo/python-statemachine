# StateChart 3.2.2

*Not released yet*

## Bug fixes in 3.2.2

### Event declarations inside `State.Compound`

A `State.Compound` (or `State.Parallel`) class body only understood the assignment form of an
event declaration (`visit_pub = bag_end.to(green_dragon)`). The two other documented forms were
silently dropped: the name was bound to a detached object and the transition it wrapped stayed
{ref}`eventless <eventless>`, firing as soon as its source state became active.

The `Event` class now declares an event inside a nested state body:

```py
>>> from statemachine import Event, State, StateChart

>>> class Journey(StateChart):
...     class shire(State.Compound):
...         bag_end = State(initial=True)
...         green_dragon = State()
...
...         visit_pub = Event(bag_end.to(green_dragon))
...
...     road = State(final=True)
...     depart = Event(shire.to(road))

>>> sm = Journey()
>>> set(sm.configuration_values) == {"shire", "bag_end"}
True

>>> sm.send("visit_pub")
>>> set(sm.configuration_values) == {"shire", "green_dragon"}
True

```

Before this fix, `Journey` started already in `green_dragon` and `visit_pub` was not among its
events. The attribute name now becomes the event `id`, an explicit `id` takes precedence, and
the `error_` / `done_state_` / `done_invoke_` prefixes expand to their dotted form.

The same applies to the `@<source>.to(<target>)` decorator, which declares an event and its
inline action at once. Inside a compound body it registered no event and never ran its body:

```py
>>> class Gate(StateChart):
...     class gate(State.Compound):
...         locked = State(initial=True)
...         unlocked = State()
...
...         push = unlocked.to(locked)
...
...         @locked.to(unlocked)
...         def coin(self):
...             return "accepted"
...
...     broken = State(final=True)
...     smash = gate.to(broken)

>>> sm = Gate()
>>> sm.send("coin")
'accepted'

>>> set(sm.configuration_values) == {"gate", "unlocked"}
True

```

Two differences from the top-level form remain, both because a nested body is evaluated before
the owning class exists: an explicit `id` that differs from the attribute name does not also
bind the attribute name, and an `Event` with no transitions is dropped instead of becoming a
class attribute.

Reported by [@Dolecor](https://github.com/Dolecor).

[#643](https://github.com/fgmacedo/python-statemachine/issues/643).

### Subclassing a chart with callbacks in a `State.Compound` body

Subclassing a `StateChart` whose compound (or parallel) body declared any callback, as a plain
method or through the `@<event>.on` / `@<event>.cond` decorators, raised
`AttributeError: 'State' object has no attribute '_callbacks'` while the subclass was being
built. The nested `State` objects are shared with the subclass, and unpacking the callbacks of
the body deleted the attribute the subclass then read. The subclass now builds, inherits the
callbacks of the base and may override the naming-convention ones as it would at the top level:

```py
>>> class Journey(StateChart):
...     class shire(State.Compound):
...         bag_end = State(initial=True)
...         green_dragon = State()
...
...         visit_pub = bag_end.to(green_dragon)
...
...         def on_enter_green_dragon(self):
...             print("A pint for Frodo")
...
...     road = State(final=True)
...     depart = shire.to(road)

>>> class Hobbit(Journey):
...     pass

>>> sm = Hobbit()
>>> sm.send("visit_pub")
A pint for Frodo

```

[#646](https://github.com/fgmacedo/python-statemachine/issues/646).

### Prefixed events were registered under a glued id

The `error_` / `done_state_` / `done_invoke_` prefixes declare two event ids, the attribute
name and its SCXML dotted form. Both reached the transition, so `send("error.execution")`
worked, but the chart registered a single event whose id was the two ids joined by a space.
`sm.error_execution()` raised `TypeError` on a bare transition and silently did nothing on an
`Event(...)`, and `allowed_events` / `enabled_events()` raised `AttributeError` looking up an
attribute named `error.execution`. The expansion also dropped the `name`, `delay` and
`internal` declared on an `Event` inside a nested state body.

Each id is now an event of its own, so both are listed, both are sendable, the attribute name
is callable as a method, and the declared arguments are kept on both. The
`@source.to(target)` decorator form, which registered only the attribute name, expands too:

```py
>>> from statemachine import Event, State, StateChart

>>> class ErrorLogger(StateChart):
...     running = State(initial=True)
...     failed = State(final=True)
...
...     error_execution = Event(running.to(failed), name="Boom")

>>> [(event.id, event.name) for event in ErrorLogger.events]
[('error_execution', 'Boom'), ('error.execution', 'Boom')]

>>> sm = ErrorLogger()
>>> [event.id for event in sm.enabled_events()]
['error_execution', 'error.execution']

>>> sm.error_execution()
>>> sm.failed.is_active
True

```

Reported by [@Dolecor](https://github.com/Dolecor).

[#644](https://github.com/fgmacedo/python-statemachine/issues/644),
[#654](https://github.com/fgmacedo/python-statemachine/issues/654).

### Events due at the same moment kept their order only by chance

Both event queues are priority queues ordered by each trigger's due time, and triggers due at
the same time came out in no particular order. A clock coarse enough to stamp two events alike
could run them out of the order they were sent or raised: twenty events raised in one callback,
all stamped with the same time, ran as `0, 2, 6, 14, 19, 18, ...`. Each trigger now also holds
the order it was created in, and triggers due at the same moment run in that order, on both
engines and both queues.

[#665](https://github.com/fgmacedo/python-statemachine/pull/665).

### Cancelling a delayed event could disorder the others and strand its caller

`cancel_event()` removed a trigger by filtering the list behind the queue's heap, and a filtered
heap is not always a heap. The triggers left could then run out of due order: of ten delayed
events due from 10 to 90 ms, cancelling the first left the one due at 50 ms running before the
one due at 40 ms. The trigger's future went with it, so on the async engine a coroutine
awaiting the cancelled event's `send()` was never answered.

A cancelled trigger now stays where it is, marked as cancelled, and is dropped when it reaches
the head of the queue, without the processing loop waiting for its due time. A coroutine
awaiting it gets `None` as soon as it is cancelled. A trigger waiting on its delay also stays
in the queue while the loop checks the clock, so a `cancel_event()` from another thread always
finds it.

[#665](https://github.com/fgmacedo/python-statemachine/pull/665).

### Delays measured on the wall clock

Every trigger was stamped with `time.time()` plus its delay, and the processing loop held a
trigger until `time.time()` reached its stamp. A step of the wall clock, from a time sync or a
change of the system time, moved every due time with it: stepped back, it held even an event
sent with no delay until the clock caught up; stepped forward, it ran delayed events early.
Delays are now measured on `time.monotonic()`, which no setting of the wall clock moves.

[#665](https://github.com/fgmacedo/python-statemachine/pull/665).

### `delay` and `internal` dropped from an explicit `Event`

`light = Event(dark.to(lit), delay=50)` rebuilt the event without its `delay`, so
`BeaconsOfGondor.light.delay` was `0` and the event fired immediately instead of being queued.
The same happened to `internal`. Each is now preserved:

```py
>>> class BeaconsOfGondor(StateChart):
...     dark = State(initial=True)
...     lit = State(final=True)
...
...     light = Event(dark.to(lit), delay=50)

>>> BeaconsOfGondor.light.delay
50

```

### `internal` declared on an `Event` ignored at trigger time

`go = Event(a.to(b), internal=True)` kept `internal` on the declaration, but neither `sm.go()`
nor `sm.send("go")` carried it to the queue, so the event always went to the external queue. Both
now honor the declaration: triggered from a callback, the event runs within the current
macrostep, before any pending external event.

Honoring it exposed how the internal queue treated a trigger that no running step had raised.
On the async engine, the first `await sm.go()` on a fresh machine was lost before the initial
state was entered. The caller got `None` instead of the callback result, and no
`TransitionNotAllowed` on a `StateMachine`. The internal queue now receives only what the
machine raises while it runs a step. Triggered from outside, an internal event goes to the
external queue and returns its result, as `send()` does:

```py
>>> class Beacons(StateChart):
...     dark = State(initial=True)
...     lit = State(final=True)
...
...     light = Event(dark.to(lit, on="kindle"), internal=True)
...
...     def kindle(self):
...         return "kindled"

>>> Beacons().light()
'kindled'

```

A delay never reached the internal queue either: `raise_("go", delay=50)` fired at once. A
macrostep takes no time, and SCXML forbids `delay` on a `<send>` to `#_internal`, so a delayed
internal event is now an invalid definition, whether declared, sent, raised, or loaded
from an SCXML, JSON or YAML `<send>` to `#_internal` (also rejected by the JSON Schema):

```py
>>> class DelayedBeacons(StateChart):
...     dark = State(initial=True)
...     lit = State(final=True)
...
...     light = Event(dark.to(lit), delay=50, internal=True)
Traceback (most recent call last):
...
InvalidDefinition: Event 'light' cannot be both delayed and internal: ...

```

Drop `internal` to deliver the event later on the external queue, or drop `delay` to run it
within the current macrostep. An explicit `send(..., internal=False)` overrides the declaration, so
`send("light", delay=50, internal=False)` delivers a declared-internal event later.

Contributed by [@chiliec](https://github.com/chiliec).

[#655](https://github.com/fgmacedo/python-statemachine/issues/655),
[#663](https://github.com/fgmacedo/python-statemachine/pull/663),
[#668](https://github.com/fgmacedo/python-statemachine/pull/668).

### `is_active` on a state nested in a parallel region

Reaching a child state through its parent (`sm.door.shut`) returned the class-level `State`,
whose `is_active` is always `False`, while `sm.shut.is_active` on the same machine was `True`.
The same happened to `parent`. A state reached through any attribute path now resolves to the
machine's per-instance proxy:

```py
>>> class Microwave(StateChart):
...     class microwave(State.Parallel):
...         my_state = State(initial=True)
...
...         class door(State.Compound):
...             shut = State(initial=True)

>>> sm = Microwave()
>>> sm.door.shut.is_active
True

>>> sm.door.shut is sm.shut
True

>>> sm.shut.parent.is_active
True

```

Creating a machine also rebound the shared `parent` of every nested state to that machine's
proxy, so with two instances alive, `parent` on the first answered for the second. Each
instance now keeps its own proxies and the class-level states are never mutated.

Reported by [@MartinBernstorff](https://github.com/MartinBernstorff).

[#651](https://github.com/fgmacedo/python-statemachine/issues/651),
[#652](https://github.com/fgmacedo/python-statemachine/pull/652).

### Each external event gets its own macrostep

With several external events already queued, the engine took them one after the other and
only then ran the internal events and eventless transitions they had enabled. An internal
event raised while handling the first external event ran after the second, breaking the
run-to-completion order the {ref}`processing model <macrostep-microstep>` describes:

```py
>>> class Beacons(StateChart):
...     dark = State(initial=True)
...     lit = State(final=True)
...     besieged = State(final=True)
...
...     signal = dark.to.itself(internal=True, on="relay")
...     light = dark.to(lit)
...     siege = dark.to(besieged)
...
...     def relay(self):
...         self.raise_("light")
...         self.send("siege")

>>> sm = Beacons()
>>> sm.send("signal")
>>> sm.lit.is_active
True

```

Each external event is now followed by its macrostep before the next one is taken, on both
engines. Eventless transitions are now checked after every external event instead of once per
batch, so a burst of queued external events costs one guard evaluation each, and an event
queued behind one that reaches a final state is no longer processed.

[#668](https://github.com/fgmacedo/python-statemachine/pull/668).

### Graphviz errors reported only the exit code

A diagram that `dot` refused to render (the `svg` format, `_repr_svg_()` in Jupyter, the
command line or the Sphinx directive) failed with `"dot" with args [...] returned code: 1`,
while the reason, such as `Error: <stdin>: syntax error in line 25 near ','`, was printed to
stdout by pydot, apart from the exception and from the Sphinx warning. These paths now run `dot` directly and raise
`GraphvizError` with the format that was requested and what Graphviz wrote to stderr. The
Sphinx directive reports the same text in its warning, and a missing `dot` says so, with a
link to the Graphviz download page.

Reported by [@barnettwilliam](https://github.com/barnettwilliam).

[#649](https://github.com/fgmacedo/python-statemachine/issues/649).

## Documentation in 3.2.2

### Platform events are not meant to be sent by user code

`error.execution`, `done.state.<id>` and `done.invoke.<id>` are raised by the engine, and SCXML
defines no external counterpart for them. The library does not tell them apart from user events:
a transition declared for one of them is listed by `allowed_events` and `enabled_events()`, and
`send()` accepts it. An external `send()` of one of them bypasses the error-handling contract. A
bare `send("error.execution")` reaches the handler with no `error` argument, and a
`send("error.execution", error=exc)` completes the transition although no action failed.
{ref}`platform-events` now states this, and the {ref}`automatic events <done-state-events>`
section links to it. No behavior changed.

Reported by [@Dolecor](https://github.com/Dolecor).

[#644](https://github.com/fgmacedo/python-statemachine/issues/644).
